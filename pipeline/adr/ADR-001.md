# ADR-001 — Compensation-Class Model for Rollback

**Resolves:** OI-REQ-05 · **Status:** ACCEPTED · **Drives:** F-14

## Context

`pipeline/requirements.md` F-14 requires three compensation classes
(REVERSIBLE / COMPENSATABLE / IRREVERSIBLE) for rollback, extending spec
§13's `ActionDefinition`, which only has `reversible: boolean` +
`rollback_action_ref: string?`. A schema-level decision is needed on how the
three-class model relates to the spec's literal boolean field.

## Options considered

**A. Replace `reversible: boolean` with `compensation_class` enum.**
Pros: single source of truth; the Policy Engine reads one field.
Cons: breaking rename from the spec's literal schema — every reference to
`reversible` across already-planned stories needs updating; loses the
simple boolean check some call sites might reasonably want.

**B. Add `compensation_class` alongside the existing `reversible: boolean`,
with a validation rule enforcing consistency between them.**
Pros: backward-compatible with spec §13 exactly as documented; unblocks
Build work referencing `reversible` today.
Cons: two fields that can drift/contradict if validation isn't enforced
(`reversible: true` + `compensation_class: IRREVERSIBLE` is representable
but nonsensical).

**C. Don't touch `ActionDefinition`; compute compensation class implicitly
at Policy Engine evaluation time from `reversible` + `rollback_action_ref`
presence + a policy annotation.**
Pros: zero schema change.
Cons: defeats the point of the three-class model, which exists specifically
to force an explicit human judgment call at action-registration time — an
implicit/derived class isn't a decision anyone actually made.

## Decision

**Option B** — additive `compensation_class` field alongside `reversible`,
with a registration-time validation rule: `reversible: true` requires
`compensation_class: REVERSIBLE`; `reversible: false` requires
`compensation_class` in `{COMPENSATABLE, IRREVERSIBLE}`.

## Rationale

Preserves the spec's literal contract — the framework's own discipline
treats spec schemas as baseline, extended additively where possible, not
renamed. Option C's implicit derivation defeats the review's actual intent
(force an explicit call). Option B's drift risk is closed by enforcing the
validation rule in `ActionConnector.validateAction()`, not left as a
convention.

## Consequences

- **(+)** No breaking change to any already-planned story referencing `reversible`.
- **(+)** Compensation class is explicitly authored, not derived — the judgment call the review asked for actually happens.
- **(–)** Two fields must be kept consistent — enforced at registration time, not just documented.
- **(–)** `rollback_action_ref` now means different things per class (direct action for REVERSIBLE; compensating-action-generator for COMPENSATABLE; unused for IRREVERSIBLE) — needs explicit field-level documentation so LLD/codegen don't treat all three uniformly.
