# ADR-002 — Engineering-Change Action Invocation Mechanism

**Resolves:** OI-REQ-03 · **Status:** ACCEPTED · **Drives:** F-19

## Context

F-19's code-change `ActionConnector` needs to resolve a `ProposedAction` by
producing an actual code/config change. Two fundamentally different
invocation shapes are possible, and the choice has direct product-UX
consequences (per `context/product-intent/vision-and-differentiation.md`'s
explicit warning against stacking two approval gates for one change).

## Options considered

**A. Full scoped `/run-pipeline` invocation** — spawn a complete Build-loop
run (planning → codegen → testgen → rfc) for one synthesized story, reusing
the supervisor's existing HIL gates, self-heal, telemetry, and budget
enforcement unmodified.
Pros: zero new orchestration code; consistent audit trail via already-built
telemetry/audit mechanisms.
Cons: heavyweight — full pipeline ceremony stacked underneath AOP's own
Approval Gate is exactly the "two gates for one change" problem the vision
doc warns against; awkward to map partial Build-loop failure states onto
AOP's `ExecutionState`.

**B. Lighter-weight direct invocation** — the connector calls codegen +
testgen directly, since AOP's own Investigation/Planning stages (§11-12)
already did the planning work a full pipeline run would redo.
Pros: avoids the double-gate problem; cleaner `ExecutionState` mapping.
Cons (identified in review): "invoke codegen + testgen directly," left
unspecified, doesn't say who enforces budgets, who checks the diff stayed
in scope, or what happens if generation drifts from the plan — under-specified
to the point of being unsafe as originally written.

## Decision

**Option B, refined**: a dedicated **`EngineeringChangeExecutor`** mediates
the invocation — not a bare direct call to two agents. Per review, this is
real, load-bearing infrastructure, not a thin pass-through.

The `EngineeringChangeExecutor`:

- accepts an already-approved, **frozen** `ResolutionPlan` — never a live or
  mutable plan;
- binds the target repository, branch, base commit, and a **permitted
  file-scope allowlist** before any generation begins;
- invokes codegen and testgen against that bound scope only;
- enforces token/time budgets, timeouts, and retry limits — the same
  discipline `loop/config/loop.config.json`'s guardrails already apply to
  the Build loop, reused here, not reinvented;
- runs the real test/lint gate — never accepts a self-reported pass;
- records every generated artifact and every gate result as `Evidence`;
- produces a **draft PR only** — never merges, never deploys;
- returns control to AOP's main verification flow (F-13) — the draft PR's
  existence and green-gate status is the evidence AOP's Verification Engine
  evaluates, not a separate verification path.

**Authorization boundary**: the AOP Approval Gate authorizes *generation of
the exact change described in the frozen plan* — not merge, not deployment.
A material deviation from the frozen plan (different files touched, scope
beyond what was bound) invalidates the authorization outright and forces
replanning — it does not proceed under the original approval.

## Rationale

The review's correction is right: a bare direct call is under-specified to
the point of being unsafe — it doesn't answer "controlled by what,
exactly." The `EngineeringChangeExecutor` is that answer. It's still not
the full Build-loop supervisor (Option A) — it's a purpose-built, narrower
control surface for this one path — so the original rationale (avoid
stacking two human-facing gates) still holds.

## Consequences

- **(+)** Matches the single-approval-gate product intent exactly.
- **(+)** `ExecutionResult` maps to one `EXECUTING` state, no sub-pipeline state to reconcile.
- **(+)** Frozen-plan binding and file-scope allowlisting make "material deviation invalidates authorization" enforceable, not just a documented expectation.
- **(+)** Draft-PR-only output means a human always makes the actual merge/deploy call outside AOP's own authority — AOP governs whether the *change* is authorized to be generated, not whether it ships.
- **(–)** Self-heal and real-test-gate logic must be extracted into something both the full Build loop and this executor can share — an LLD-level refactor of what's currently only in `supervisor.md`'s pseudocode, not free.
- **(–)** Two orchestration paths through the same underlying agents means test coverage must prove behavioral consistency between them.
- **(–)** The `EngineeringChangeExecutor` is now real, non-trivial infrastructure (budget enforcement, scope-binding, deviation detection) — bigger LLD/Build surface than the original "just call two agents" framing implied.
