# ADR-003 — Risk Classification for Engineering-Change Actions

**Resolves:** OI-REQ-04 · **Status:** ACCEPTED · **Drives:** F-19, F-08
**Builds on:** ADR-002 (invocation mechanism), ADR-001 (compensation class, reused as one component)

## Context

F-08's Policy Engine computes effective risk from registered action risk,
environment, parameters, blast radius, policy tags, and evidence history
(spec §15). Operational actions have a natural `blast_radius.scope`. Code
changes don't map onto that shape directly.

## Options considered

**A. Reuse `blast_radius.scope` unchanged**, mapped by convention.
Cons: conflates code-change risk with runtime blast radius.

**B. Add a code-change-specific risk-scoring input set**, feeding a
computed value into `blast_radius.estimated_entities`.
Cons (identified in review): "tenant-configurable registered scoring
function," left unconstrained, is a code-injection surface into the one
component whose entire value is deterministic authority — arbitrary
tenant-supplied executable code must never run inside the control plane.
Also: collapsing blast radius into one number understates it regardless of
how that number is computed.

## Decision

**Option B, refined — declarative scoring only, producing a
multi-component blast-radius model, not a single number.**

**Blast radius components** (all scored independently, not folded into one
value):

| Component | Source |
|---|---|
| `estimated_entities` | existing field (spec §4.3) — files/lines-changed-derived proxy |
| `environmental_criticality` | which environment + how critical the touched service is |
| `compensation_class` | REVERSIBLE / COMPENSATABLE / IRREVERSIBLE — **reused from ADR-001, not re-derived** |
| `data_sensitivity` | does the touched code path handle sensitive data |
| `customer_exposure` | internal-only vs. customer-facing surface |

**Scoring mechanism constraints** (per review, non-negotiable for v1):

- **Declarative rules only** — no arbitrary executable code (no
  tenant-supplied JavaScript or equivalent) runs inside the control plane.
- **Registered and versioned**, like any other config artifact.
- **Deterministic and side-effect-free** — same input always produces the
  same component scores (preserves NFR-05's determinism guarantee, which
  this scoring feeds into).
- **Schema-validated on registration**, not only at evaluation time.
- **Bounded input size and a hard time budget** at evaluation.
- **Hash-bound to the `PolicyDecision`** it informed — the exact scoring
  rule version used is part of the auditable record.
- **Explainable** — the component scores themselves are the explanation,
  never a black-box output.
- **Default-deny on evaluation failure** — a broken input, timeout, or
  malformed config denies the action; it is never silently treated as
  low-risk.

If executable plugins are ever needed beyond what declarative rules can
express, they run in an isolated, sandboxed connector runner — never inline
in the control plane. Not scoped for v1.

## Rationale

"Tenant-configurable" without constraints is a code-injection surface into
the Policy Engine's determinism guarantee (NFR-05) — the review's concern is
correctness-critical, not stylistic. Declarative-only, bounded, versioned,
default-deny closes that surface entirely. The component model directly
addresses "a single entity count cannot represent the entire blast radius"
— five named, independently-auditable dimensions instead of one derived
integer.

## Consequences

- **(+)** No code-injection surface in the control plane.
- **(+)** Component scores are individually auditable and explainable, not a single opaque number.
- **(+)** Default-deny-on-failure means a broken scoring config fails safe, not silently permissive.
- **(+)** `compensation_class` reuse (not re-derivation) keeps ADR-001 as the single source of truth for that dimension.
- **(–)** Declarative rules are less expressive than executable code — some nuanced scoring logic may not be representable in v1's rule language; a real LLD constraint to design the rule language against, not a footnote.
- **(–)** Five components instead of one field is more surface for LLD to design and for codegen/testgen to validate — larger scope than the original single-`estimated_entities` framing implied.
