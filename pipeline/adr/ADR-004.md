# ADR-004 — Orchestrator Crash Recovery & Idempotency Mechanism

**Resolves:** OI-REQ-06 · **Status:** ACCEPTED · **Drives:** F-03

## Context

F-03's failure/recovery acceptance criteria require that a worker crash
occurring after an external mutation completes but before the transition
persists must never result in a blind retry of that mutation.

## Options considered

**A. Idempotency-key-only recovery** — rely purely on `execute()`'s
idempotency key; every connector must make `execute()` itself safely
re-callable.
Cons: every connector author must correctly implement idempotent
`execute()` — an easy rule to get wrong, with a costly failure mode.

**B. Orchestrator-side write-ahead marker** — before calling `execute()`,
persist a lightweight "attempted" marker; on restart, a mandatory status
check runs before any retry.
Cons (identified in review): a stable correlation key wasn't specified as
part of the marker, and "mandatory status-check-before-retry" doesn't say
what happens when the status check itself can't produce an answer.

## Decision

**Option B, refined.** The write-ahead marker carries a stable
**`operation_id`** — the same idempotency key shape spec §31 already
defines (`tenant_id + request_id + plan_id + step_id + action_version`) —
passed to the connector on every `execute()` call, not just recorded
orchestrator-side. On restart, the mandatory status check queries the
connector using this same `operation_id`.

**Fail-closed correction (per review):** if the external system cannot
answer the status check — connector doesn't support correlation, or the
query itself fails or times out — **automatic retry is prohibited**, not
attempted and not assumed safe, unless the action is provably idempotent by
construction (e.g. a pure upsert with no side-effect-on-repeat). Absent
that proof, the default is: surface for human decision, never guess.

## Rationale

The original decision assumed a status check always succeeds in resolving
ambiguity. The review correctly identifies that a status check can itself
be ambiguous or unavailable — "mandatory" was doing more work than the
mechanism actually guaranteed. Prohibiting retry absent proof of
idempotency is the fail-closed version of the same principle this review
applies consistently across ADR-003 and ADR-008: uncertain state defaults
to the safer, more restrictive outcome, never an optimistic one.

## Consequences

- **(+)** Centralized recovery logic; connectors only need to expose a status check keyed on `operation_id`, a lower bar than full internal idempotency.
- **(+)** `operation_id` correlation makes status checks actually meaningful, not best-effort.
- **(+)** The fail-closed default (no retry without proof) closes the exact ambiguity gap the review identified.
- **(–)** `ActionConnector`'s interface now requires an explicit, testable idempotency contract per connector (does it support correlation? is `execute()` provably idempotent for this action?) — not assumable, must be declared and verified at registration.
- **(–)** An action stuck in "attempted, unknown, not provably idempotent" now requires human intervention to resolve — a real operational burden the mechanism surfaces rather than eliminates.
- **(–)** The marker write needs its own delivery guarantee — this ADR assumes ADR-005's mechanism covers it.
