# ADR-005 — Evidence Ledger Write-Durability Mechanism

**Resolves:** OI-REQ-07 · **Status:** ACCEPTED · **Drives:** F-03, F-15
**Relates to:** ADR-004 (its marker write needs this mechanism)

## Context

F-03's acceptance criteria require that a failed `Evidence` write causes the
whole transition to be treated as failed and retried — not silently
skipped. This needs a mechanism that's actually true under real failure
conditions (DB unavailable, network partition), not just true when nothing
goes wrong. RULE 7 (CONTEXT.md) requires state + event + evidence, "all
three, every time" — but a DB write and an event-bus publish can't literally
be one atomic operation.

## Options considered

**A. Synchronous, same-transaction write** — state transition + evidence
write in a single DB transaction; either both succeed or both roll back,
relying on the orchestrator's existing transient-failure retry logic (spec
§30).
Pros: simplest mechanism; no new infrastructure; "all three" becomes
literally atomic for the state+evidence pair.
Cons: couples orchestrator availability to the primary database's
availability for every transition; doesn't address `PlatformEvent`
emission at all — that's a separate concern (typically pub/sub), and a
single DB transaction can't make an external event-bus publish atomic with
a DB write.

**B. Outbox pattern for events** — state + evidence write to the DB in one
transaction (as in A); `PlatformEvent` emission writes to an outbox table in
the *same* transaction, with a separate relay process publishing from the
outbox asynchronously, retrying until acknowledged.
Pros: solves both problems — state+evidence atomicity (same as A), and
event emission gets an at-least-once delivery guarantee without the
orchestrator blocking on the event bus.
Cons: real new infrastructure — outbox table, relay process, relay-lag
monitoring; operational cost for a guarantee only exercised during actual
failures.

## Decision

**Split mechanism**: Option A (same-transaction) for the `ExecutionState` +
`Evidence` pair — they're already in the same relational store and don't
need outbox complexity. **Option B (outbox + relay)** specifically for
`PlatformEvent` emission, where a real atomicity gap exists.

## Rationale

Treating all three writes identically either overstates what one DB
transaction can guarantee (can't make an event-bus publish atomic with a DB
write) or over-engineers state+evidence with outbox machinery they don't
need. Matching the mechanism to what's actually being guaranteed avoids
both.

## Consequences

- **(+)** State+evidence atomicity is genuinely free — same transaction, same store.
- **(+)** Event delivery gets a real guarantee instead of best-effort publish-and-hope.
- **(–)** The outbox relay is a new operational component needing its own health metric (extending `context_connector_error_rate`-style monitoring, spec §29, to cover relay lag) and its own Build story.
- **(–)** Event consumers (Control Tower, future subscribers) must tolerate at-least-once delivery — duplicate events are possible and must not be assumed away — a downstream design constraint for LLD.
