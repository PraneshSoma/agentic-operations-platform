# ADR-006 — Role-Separated Review as a Verification Input

**Resolves:** OI-REQ-01 · **Status:** ACCEPTED · **Drives:** F-17

## Context

The Confidence Engine mockup in `vision-and-differentiation.md` includes
"Independent review ✓" — a second model reviewing the first's output — as
one itemized check feeding confidence. Spec §19's `VerificationResult` has a
generic `checks[]` array that can hold this, but there's no defined check
type or contract for what it evaluates.

## Options considered

**A. Model diversity** — pass/fail based on a genuinely different model
reaching a compatible conclusion.
Cons: a second model call on every governed action (cost, latency);
"materially disagrees" isn't well-defined without a structured rubric.

**B. Role diversity** — reuse `loop/agents/review.md`'s existing audit
discipline, applied per-change instead of per-PR-batch.
Cons (identified in review): calling same-model-family review "independent"
overstates it — two passes from the same model family are correlated
regardless of prompt differences.

## Decision

**Option B, refined and renamed: "role-separated review," not "independent
review."** The terminology correction matters — this mechanism should never
be described to stakeholders or on the dashboard as "independent."

The role-separated reviewer:

- runs `review.md`'s discipline as a distinct pass, per-change;
- receives **only** the frozen plan, the diff, the test results, and the
  evidence already gathered — explicitly **not** the generator's reasoning
  transcript or chain-of-thought. Context isolation is what makes this a
  genuinely separate judgment, not a second pass over the same reasoning
  wrapped in a different prompt;
- produces its own, separately-generated verdict.

Genuine model diversity (Option A) remains the Extension point, unchanged —
still available, still not the MVP default, now clearly the thing that
would actually earn the word "independent."

## Rationale

The correlated-error concern is specific and real: same-model-family review
shares blind spots with the generator by construction, regardless of prompt
differences. Context isolation (excluding the reasoning transcript) is a
concrete, cheap, implementable mitigation — the difference between
reviewing the work and re-reading the same explanation and agreeing with
it.

## Consequences

- **(+)** Ships a real, working role-separated review signal from day one using existing agent infrastructure.
- **(+)** Tenants wanting genuine model diversity can register it later without a runtime change.
- **(+)** Naming it accurately ("role-separated," not "independent") prevents stakeholders from over-trusting a same-model-family signal.
- **(+)** Context isolation is a real, enforceable mitigation for correlated error, not just an acknowledged limitation.
- **(–)** `VerificationResult.checks[].name` needs a formal enum/taxonomy so this is a recognized, structured check type, not a free-text label — LLD-level.
- **(–)** Excluding the reasoning transcript means the reviewer can't flag "the generator's stated reasoning doesn't match what it actually did" as a distinct failure mode — a real limitation of context isolation, worth naming even though the isolation itself is the point.
