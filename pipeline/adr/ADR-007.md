# ADR-007 — Confidence Dimension: Source Reliability

**Resolves:** OI-REQ-08 · **Status:** ACCEPTED · **Drives:** F-17

## Context

F-17 names "source reliability" as one of two confidence dimensions with no
existing contract field to back it. A definition and computation basis are
needed before it can be surfaced.

## Options considered

**A. Static, connector-type-based reliability** — each `ConnectorDescriptor.type`
gets a fixed, tenant-configured reliability weight.
Cons (identified in review): type-level granularity conflates connectors
that may have very different real reliability even within the same type; a
raw decimal weight (e.g. `0.83`) implies a precision the underlying data
doesn't support.

**B. Empirical, historical-accuracy-based reliability** — derive a score
from `Evidence.relationships.contradicts`/`supports` history.
Cons: requires evidence volume to be meaningful; needs a defined cold-start
behavior.

## Decision

**Option A, refined.** Reliability weight attaches to **`(tenant_id,
connector_definition_ref, connector_version)`** — not a global
`ConnectorDescriptor.type` lookup. Two connectors of the same `type` (e.g.
two different `logs` connectors) get independently configured,
independently versioned reliability classifications.

Weights are expressed as **ordinal levels — `LOW | MEDIUM | HIGH |
AUTHORITATIVE`** — not decimal scores. An uncalibrated `0.83` claims
scientific precision the underlying data doesn't support; an ordinal level
makes the same judgment honestly.

**Option B remains the intended evolution**, unchanged from Revision 1, once
sufficient evidence volume exists per connector instance.

## Rationale

Type-level granularity conflates connectors that may have very different
real reliability — the review's correction is a genuine precision
improvement, not a preference. Ordinal levels are honest about what a
day-one, uncalibrated default can actually claim, consistent with the same
false-precision concern raised elsewhere in this batch (ADR-008's DENY/
certainty framing makes the identical point).

## Consequences

- **(+)** Per-connector-instance-and-version granularity means a bad connector doesn't drag down every other connector of its type.
- **(+)** Ordinal levels are honest about what a day-one, uncalibrated default can actually claim.
- **(+)** Clean upgrade path to Option B still reuses existing `Evidence.relationships` fields — no schema migration needed later.
- **(–)** More configuration surface — a tenant now configures reliability per connector *instance and version*, not once per type; more registry entries to maintain.
- **(–)** The transition threshold from Option A to Option B (how much evidence volume is "enough") still needs its own decision, unresolved here.
