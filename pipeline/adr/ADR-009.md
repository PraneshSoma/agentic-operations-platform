# ADR-009 — Secret Management Strategy

**Resolves:** OI-CTX-08 (architecture portion) · **Status:** ACCEPTED · **Drives:** all connectors

## Context

Spec §24 requires secrets never be inline. `CONTEXT.md` already states an
intended default ("`SecretResolver` interface... AWS Secrets Manager to
start") — but that was a placeholder, not a ratified decision, and
Tenant #1's actual cloud platform/secret manager remains unknown
(OI-CTX-08).

## Options considered

**A. Single concrete implementation now (AWS Secrets Manager), no
abstraction layer.**
Pros: least code for the pilot; directly usable if Tenant #1 turns out to be
AWS-based.
Cons: if the guess is wrong, this is a rewrite, not a config change —
directly contradicts NFR-01 at the one place secrets touch every connector.

**B. `SecretResolver` interface with a pluggable implementation** — a
local-dev, env-var-backed implementation ships now; the concrete cloud
implementation is deferred until Tenant #1's platform is confirmed.
Connectors code against the interface only, never a concrete SDK directly.
Pros: matches NFR-01 exactly; unblocks Build work now without committing to
a guess; swapping the concrete implementation later is additive
configuration, not a connector rewrite.
Cons: the interface must anticipate a shape multiple secret managers can
satisfy (reference-based lookup, rotation awareness) without knowing the
real target — some risk of designing for the wrong abstraction if the
eventual target has an unusual shape.

## Decision

**Option B** — formalizes `CONTEXT.md`'s existing placeholder as an accepted
decision: `SecretResolver` interface, env-var-backed local implementation
now, concrete cloud implementation deferred and tracked against OI-CTX-08's
resolution at tenant onboarding.

## Rationale

Option A's rewrite risk is exactly the scenario-specific coupling the whole
platform exists to avoid — secrets handling is not the place for an
exception. Option B's downside (designing an abstraction before knowing the
real target) is bounded: the interface only needs reference-resolution and
secret-never-in-context, both fully specified by spec §24 regardless of
which concrete manager backs it.

## Consequences

- **(+)** Build work on every connector proceeds without blocking on tenant onboarding.
- **(+)** Swapping to the real secret manager, once known, is additive — a new registered implementation, not a connector-by-connector change.
- **(–)** The interface's exact shape (rotation handling, caching, resolution-failure semantics) must be designed generically now — LLD-level, worth validating against at least one real cloud SDK shape before considering it settled.
- **(–)** OI-CTX-08 remains genuinely open — this ADR resolves the *architecture* question, not the *tenant fact*. Tracked separately for tenant onboarding.
