# ADR-011 — Evidence Retention & Compliance Posture

**Resolves:** OI-CTX-10 (architecture portion) · **Status:** ACCEPTED · **Drives:** F-15

## Context

Spec §21/§22 already require append-only, hash-chained evidence with a
`retention_class` field (§4.6), but no concrete retention periods or
handling rules are defined, and Tenant #1's actual compliance regime is
unknown (OI-CTX-10).

## Options considered

**A. Wait for OI-CTX-10 to resolve** before defining any retention policy.
Cons (unchanged from Revision 1): blocks any real testing of retention
*enforcement* until tenant onboarding — expensive to retrofit onto an
already-running ledger with real data in it.

**B. Indefinite retention, unenforced** (Revision 1's decision). **Rejected
on review**: indefinite retention is not conservative. Unbounded retention
*increases* privacy, security, legal, and cost exposure — it optimizes
against one failure mode (deleting something a regime required kept) while
ignoring the opposite one (retaining something a regime required deleted,
e.g. a right-to-erasure obligation) and the ongoing cost/exposure of
unbounded growth. Not knowing the compliance regime is a reason to avoid
*destructive* deletion by default — it is not a reason to default to
unbounded production retention.

**C. Finite, class-differentiated retention with an explicit non-production
label** (new, decided below).

## Decision (Revision 2)

**Option C.** Retention is:

- **Class-differentiated**, not one policy for everything — separate rules
  for operational state, prompts, evidence records, secrets-redacted
  payloads, and audit hashes. These have genuinely different retention
  needs (an audit hash chain plausibly wants to live longest; a raw prompt
  log plausibly wants the shortest, most conservative default).
- **Explicit `retention_class` + configurable expiration** per spec §4.6's
  existing field — populated with real, finite values, not left unenforced
  indefinitely.
- **Legal-hold override** — a class can be pinned past its normal
  expiration when required, as an explicit, audited action, not the
  default state of everything.
- **Finite for development** — the dev/prototype environment uses a
  bounded, clearly-labeled default (e.g. 90 days), explicitly marked:

  > **Development-only temporary behavior — not an approved production
  > default.**

- **Mandatory tenant decision before production onboarding** — no tenant
  goes live without an explicit, documented retention decision per class.
  The finite dev default is a placeholder that expires with the prototype,
  not something that silently becomes "the policy" by inertia.

## Rationale

The review's correction is right and Revision 1's error was specific:
treating "avoid destructive deletion" (a genuinely safe default) as
equivalent to "retain everything, unenforced, indefinitely" (an unbounded
liability, not a safe default). Class-differentiation replaces a single
retain/delete binary with the granularity spec §4.6 already provides for —
`retention_class` exists precisely so different evidence types can be
treated differently; Revision 1 defined the field but didn't use its
expressiveness. The explicit dev-only label prevents the realistic failure
mode: an "indefinite by default" decision silently becoming a production
posture through inertia.

## Consequences

- **(+)** No unbounded production liability by default — the failure mode the review flagged is closed.
- **(+)** Class-differentiation matches real regulatory shape — audit trails and raw operational logs are not interchangeable retention problems.
- **(+)** The explicit dev-only label prevents silent production drift.
- **(–)** Real design work now required before any Build story can implement retention correctly: five classes need real default values, not one blanket policy — larger LLD surface than Revision 1 implied.
- **(–)** "Mandatory tenant decision before production onboarding" is a process gate this repo can document but can't itself enforce technically — worth a Build story that actually blocks tenant activation without a recorded retention decision, not just documentation of the requirement.
