# ADR-012 — Identity Model & Provider Integration for ExecutionAuthorization

**Resolves:** OI-CTX-12 (architecture portion) · **Status:** ACCEPTED · **Drives:** F-09, and now also F-06, F-08, F-11 (identity touches more than F-09 alone)

## Context

Revision 1 deferred identity-provider integration entirely, reasoning that
F-09 (OBO) is Post-MVP and MVP's simulated action doesn't need it. Review's
correction: **provider integration** (OIDC, workforce federation, cloud
OBO) can be deferred — but a **minimal identity model** cannot, because
MVP's simulated pipeline already has real identity questions that aren't
about OBO at all: who submitted the trigger, who approved the action, which
tenant they belong to, which roles they hold, whether the approver is
permitted to approve that risk class, and whether proposer/approver
separation is required. These are load-bearing for F-06 (frozen
plan/approval), F-08 (policy routing by role), and F-11 (halt-role
authorization) — not F-09 alone.

## Options considered

**A. Build generic OIDC-based identity resolution now.** (Unchanged from
Revision 1 — still rejected: premature provider-specific work ahead of when
F-09 needs it.)

**B. Defer identity-provider integration entirely, including the identity
model itself.** (Revision 1's decision.) **Rejected on review**: conflates
"defer the external provider" with "defer having any identity model," when
F-06/F-08/F-11 already need to answer "who is this actor and what are they
permitted to do" well before F-09's OBO requirement ever triggers.

**C. Build `IdentityResolver` now, with a local development implementation
using fixed development principals; defer only the external provider
integration.** (New, decided below.)

## Decision (Revision 2)

**Option C.** `IdentityResolver` is built **now** — an interface (mirroring
`SecretResolver`'s pattern from ADR-009) that resolves an actor reference
to: identity, `tenant_id`, roles, and whether that identity is permitted to
approve a given risk class. The **local development implementation** is a
fixed, config-defined set of development principals (e.g. a small
YAML/JSON list of `{id, tenant_id, roles}` entries) — no external call, no
real SSO.

What's still deferred, matching Revision 1's original intent: the
**concrete external integration** — OIDC, workforce federation,
cloud-provider OBO token issuance. That work waits for F-09/OI-CTX-12's
real resolution, unchanged.

Concretely, `IdentityResolver` must answer, from day one:

- who submitted the trigger (resolves `IncomingRequest.requester`);
- who approved the action (resolves `ApprovalDecision.actor`);
- which tenant they belong to;
- which roles they hold;
- whether the approver's roles satisfy the risk class being approved (feeds
  F-08's policy routing);
- whether proposer/approver separation is required and satisfied (a role
  cannot both propose and approve the same action where policy requires
  separation).

## Rationale

Revision 1's mirrored-deferral argument (same pattern as ADR-009) turns out
not to hold on inspection: secrets genuinely have zero MVP need before a
real connector exists — nothing in F-01 through F-13 touches a secret.
Identity is different — F-06's approval step and F-08's policy routing
already need to know *who* is acting, using simulated/development
principals, well before any real OBO token is ever issued. Conflating
"defer the provider" with "defer the model" was the actual error;
separating them is what Option C does.

## Consequences

- **(+)** F-06/F-08/F-11 have a real identity model to build against from the start — not stubbed with untyped strings that would need retrofitting later.
- **(+)** The local development implementation is cheap (a static config list) — this isn't premature infrastructure investment, just making an already-necessary concept explicit instead of implicit.
- **(+)** `IdentityResolver`'s interface, designed now, is the same interface F-09's real provider implementation plugs into later — no interface redesign needed when OI-CTX-12 resolves.
- **(–)** This is more MVP-scope work than Revision 1 implied — `IdentityResolver` plus its development-principal implementation is a real Build story, not free.
- **(–)** "Fixed development principals" must be clearly labeled as non-production (same discipline as ADR-011's dev-only retention default) so a real pilot doesn't accidentally run on placeholder identities.
